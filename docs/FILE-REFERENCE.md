# File reference

Every file in the repo and what it does. Generated by reading the code, not
the docs — where a comment and the behaviour disagreed, the behaviour won.

Files marked **DEAD** are superseded and should not be run or edited.
Files marked **BROKEN** throw against the current schema.

## Root

| File | What it does |
| --- | --- |
| `package.json` | No application code. Holds the `concurrently` scripts that run the API and the frontend together (`npm run dev`), plus the `db:load` / `db:reset` / `build` / `lint` / `typecheck` pass-throughs to the sub-projects. |
| `package-lock.json` | Lockfile for that one dev dependency (`concurrently`). |
| `.gitignore` | Applies to the whole tree recursively. Ignores `node_modules/` at any depth, `.env` and `.env.*` (but keeps `.env.example`), `.next`, `*.tsbuildinfo`. |
| `README.md` | Setup, architecture, conventions, branch and pull request rules, troubleshooting table, known gaps. The primary onboarding document. |
| `.github/workflows/ci.yml` | CI (KAN-281). On every pull request into `main` and every push to it, three jobs: **API tests** (the backend suite against a PostgreSQL 16 service), **Browser tests** (builds the site and runs the Playwright tests in `e2e/` on desktop and phone sizes; keeps screenshots, traces and the API log when a test fails) and **Frontend checks** (lint, typecheck, production build). The `main` ruleset requires them to pass before a pull request can merge; no approval is needed (KAN-32). |
| `e2e/` | Browser tests (Playwright). `global-setup.ts` loads the `shahebbazar_e2e` database, builds the site into `.next-e2e`, and starts the API (port 4200) and the site (port 3200); `fixtures.ts` has `signIn`, `sql`, the sign-in code reader and a check that fails any test with browser console errors; `tests/` covers visitors, sign-in, customers, business owners and admins. See `e2e/README.md`. |
| `.github/pull_request_template.md` | The checklist every pull request starts with: Jira key, tests, access matrix, migrations, docs, no secrets. |

## backend/ — Express API, port 4000

| File | What it does |
| --- | --- |
| `package.json` | Declares Express 5, `pg`, `cors`, `dotenv`, `multer`. Scripts: `dev` uses `node --watch` for reload on save. **`socket.io` is declared but never imported anywhere** — presumably intended for the messaging feature. |
| `.env.example` | Template for `backend/.env`. Postgres connection vars, `PORT`, `CORS_ORIGIN`. Copy it, then set `PGPASSWORD` — nothing connects until you do. |
| `db.js` | The entire database connection layer, 11 lines. Loads `.env` via dotenv, creates one `pg.Pool`, exports it. Every route file `require`s this same pool — Node caches modules, so there is exactly one pool per process. Connects lazily: creating the pool does not touch Postgres. |
| `index.js` | Server entry point. Registers middleware **in order** (CORS → JSON body parser → static `/uploads` → three routers → `/api/health` → `/`), starts the listener, prints the schema report at startup, and handles `EADDRINUSE` with the `npx kill-port` remedy instead of a stack trace. |
| `lib/verifySchema.js` | Checks that the 14 tables and views the API depends on actually exist, in **one** query, using `to_regclass()` (which returns NULL for a missing object instead of raising). | `routes/public.js` | The real API. 478 lines, all read-only, all approved-rows-only. Serves `/api/home`, `/api/categories`, `/api/businesses`, `/api/businesses/:slug`. | `routes/analytics.js` | `POST /api/track/search` and `POST /api/track/view`. Writes `search_logs`, `vendor_search_impressions` and `vendor_profile_views`. ## database/

The database is built from one consolidated baseline. `database/README.md`
covers the commands and how schema changes are made.

| File | What it does |
| --- | --- |
| `baseline/schema.sql` | The complete schema: 27 tables and 4 views covering accounts and sign-in, locations, categories, businesses, listings and photos, quotations, messaging, reviews, moderation and analytics. Enables `pg_trgm`. Status columns use `CHECK` rather than `ENUM` so extending them is a one-line change. |
| `baseline/seed.sql` | Sample data: the location hierarchy (Bangladesh → Rajshahi → areas), categories, businesses, listings, accounts for every role, reviews, events and sixty days of analytics. |
| `seed-assets/` | The images the seed references as `uploads/<file>`; `db:load` copies them into the upload folder. |
| `checks/verify-baseline.sql` | Returns a row for anything missing. Run by `db:load` and `db:verify`. |
| `snapshots/current-schema.sql` | Schema-only dump of a freshly loaded database, for reviewing differences. |
| `legacy/` | Historical `schema.v2*.sql` / `seed.v2*.sql` files, the original `schema.sql` and `sampleinput.sql`, and `SCHEMA-NOTES.md` (why v2 differs from v1, mapped to the client's scope email). Reference only; never loaded. |

### The four views

| View | Purpose |
| --- | --- |
| `v_business_cards` | Public card projection. Derives primary category, rating, review count and today's open state via `LEFT JOIN LATERAL`, and ends in `WHERE vendor_status = 'approved'` — which is why unapproved shops 404 with no explicit check in the route. `open_state` is three-valued: `open`, `closed`, or NULL meaning *hours unknown*. |
| `v_search_trends_daily` | Popular-search chips and admin trends. `HAVING COUNT(*) >= 5` suppresses rare terms, so one person's query cannot become a "popular search" or re-identify them. |
| `v_active_users_daily` | Distinct visitor hashes per day, across profile views and searches (v2.4). Never counts accounts. |
| `v_moderation_queue` | `UNION ALL` of pending vendors + pending listings + open reports into one admin list. |

### lib/ — the four files that carry the logic

| File | What it does |
| --- | --- |
| `api.ts` | The only file that knows the API exists. `getHomeData()`, `searchBusinesses()`, `getBusiness(slug)`, plus `assetUrl()`. All run server-side. Sets the cache window per endpoint (home and profile 300s, search 60s) via `next: { revalidate }`. Two deliberate failure policies: `getHomeData` swallows errors and returns empty arrays so the page shell still renders; `getBusiness` rethrows anything but a 404, because a half-rendered profile looks complete and is wrong. `assetUrl()` turns a stored relative path into an absolute browser URL and normalises Windows backslashes. |
| `types.ts` | The API contract as TypeScript interfaces, field names matching the database columns exactly. Change a column in Express without changing this and `npm run typecheck` fails — the mismatch surfaces at compile time instead of as blank fields. Documents the `pg` NUMERIC-returns-a-string trap. |
| `i18n.ts` | Every user-facing string in English and Bangla, 331 lines. Plus `resolveLocale()` (reads `?lang=`), `localeHref()` (appends it to links so the language survives navigation), and `pick(locale, en, bn)` which falls back to the other language when a translation is null, so a field is never rendered empty. No hardcoded English in JSX — that is a hard rule. |
| `format.ts` | Display formatting, server-side only. `toNumber` (the NUMERIC-string fix), `formatRating`, `formatClockTime` (SQL `TIME` → "9:30 AM"), event date helpers pinned to `Asia/Dhaka`, and `localiseDigits` which maps ASCII digits to Bengali numerals. Timezone is pinned because formatting the same date on both server and client produces a hydration mismatch. |

`seo.ts` (outside the four) builds every public page's metadata through `pageMetadata()`: title, description, canonical URL, and complete OpenGraph and Twitter tags. It exists because Next.js merges metadata shallowly, so a page that sets `openGraph` at all loses the layout's site name, locale and image. `NEXT_PUBLIC_SITE_URL` must be the real domain in production, or every canonical and share link points at localhost.

`analytics.ts` (outside the four) is browser-side: `sendAnalytics()` posts a beacon and never throws, and `viewSource()` works out whether a profile was reached from search, a category page, a shared link or directly. It remembers the previous path itself, because `document.referrer` does not change on client-side navigation.
