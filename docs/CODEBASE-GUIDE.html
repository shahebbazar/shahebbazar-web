Shaheb Bazar, end to end

A local business directory for Rajshahi, Bangladesh. Three processes — a Next.js site, an Express API, a PostgreSQL database — and this is every seam between them: what each one does, what it sends, and where it currently breaks.

Next.js 16 · :3000 → Express 5 · :4000 → PostgreSQL 15+ · :5432

The shape of it

Three tiers, each with exactly one job, talking in one direction only. Nothing skips a tier, and nothing talks backwards.

Weblocalhost:3000
Next.js — renders HTML

Reads the URL, calls the API on the server, and returns finished HTML. It never queries Postgres and it holds no business logic beyond formatting.

↓  fetch(process.env.API_BASE_URL + "/api/…") — server-to-server HTTP, invisible to the browser
APIlocalhost:4000
Express — turns URLs into SQL

Validates and clamps query parameters, runs SQL through a connection pool, shapes the rows into JSON. Also serves uploaded images from backend/uploads/.

↓  pool.query(sql, params) — parameterised, over the pg pool
DBlocalhost:5432
PostgreSQL — stores and derives

18 tables, 4 views. The views do real work: ratings, "open now", the moderation queue. Only vendor_status = 'approved' rows are ever visible to the public.

The one rule that shapes the whole frontend

Every public page fetches its data on the server, during rendering — never in a useEffect in the browser. That single rule is why the pages are structured the way they are.

The client requirement is that shop pages must be crawlable by Google. A page that fetches in the browser sends Googlebot an empty <div>, because the crawler does not reliably wait for JavaScript to fill it in. A page that fetches on the server sends complete HTML with every shop name, rating and phone number already in it.

So: app/(public)/page.tsx is an async function that awaits data before returning JSX. There is no loading spinner, no useState, no client-side data code anywhere in the public surface.

Server component vs client component. In the Next.js App Router every file is a server component by default — it runs once, on the server, and its JavaScript is never sent to the browser. Adding "use client" at the top opts a file into the browser: it can use useState, useEffect and event handlers, and its code ships to the user.

In this repo only four files are client components, and all four are the older vendor pages. Everything on the public browsing surface is a server component.

02

The database

PostgreSQL, 18 tables and 4 views, split across three additive schema files. The design decisions here drive everything above them.

Naming conventions, and why they matter

Three rules, applied without exception:

  • Table names are snake_case plural — vendors, categories, quote_requests.
  • Column names are prefixed with their table — vendor_name, category_slug, review_rating.
  • Foreign keys are <table>_id — vendor_id, user_id, location_id.

The prefixing looks redundant until you write a five-table join. SELECT name FROM vendors JOIN categories … is ambiguous; vendor_name and category_name are not. It also means a field name never changes as it travels: the column vendor_slug is vendor_slug in the SQL, in the JSON response, and in the TypeScript interface. You can trace any value back to its source without a translation table.

The nine sections of the schema

1 · Identity and access
users, otp_codes, sessions

One users table for all three roles, discriminated by user_role (customer / vendor / admin). Phone is the primary identifier, stored E.164, because the client asked for phone-OTP login; email is optional and nullable.

otp_codes stores a hash of the code, not the code, so a database leak does not hand over working login codes. sessions likewise stores session_token_hash — the real token lives only in an httpOnly cookie.

None of these three tables is written to yet. Authentication does not exist. This is the single largest gap in the project.

2 · Geography
locations

A self-referencing hierarchy: country → division → district → city → area. Rajshahi's areas — সাহেব বাজার Shaheb Bazar, Laxmipur, Kazla, Talaimari, Binodpur — are type = 'area' rows under rajshahi-city.

location_path is a materialised ancestry string (bd/rajshahi-division/rajshahi-district/rajshahi-city/kazla) with a text_pattern_ops index, so "everything under Rajshahi" is a prefix match rather than a recursive query. Expanding to a new city is an INSERT, not a migration.

3 · Taxonomy
categories

Also self-referencing: top-level categories (Medical, Tourism, Restaurants, Shopping, Education, Services) each have children. category_slug is the public URL segment. category_icon holds a string key like "medical", resolved to a React icon component at runtime — this is the one place the frontend cannot import an icon directly.

Every user-facing name has a _bn twin: category_name and category_name_bn.

4 · Vendors
vendors, vendor_categories

The business profile. Note it does not hold credentials — user_id points at the owning account, so one person can own several businesses.

vendor_status is the moderation gate: draft / pending / approved / rejected / suspended. Only approved is ever public. vendor_is_featured is paid placement, and it is a hard requirement that featured rows render with a visible label.

vendor_categories is a plain many-to-many join table — a shop can sit in several categories.

5 · Listings
vendor_listings, listing_photos

The products and services a shop sells. Prices are a range (listing_price … listing_price_max) with a CHECK that max ≥ min, plus a unit and a minimum order quantity — this is a B2B directory, so "৳450 per kg, minimum 50 kg" is the normal case.

listing_photos has a partial unique index: UNIQUE (listing_id) WHERE photo_is_primary. At most one primary photo per listing, enforced by the database rather than by hoping the application remembers.

6 · Quotations
quote_requests, quote_responses

The Phase-1 monetisation path. A buyer files an RFQ; sellers respond with a price. Money is settled off-platform — no payment gateway until Phase 2.

An RFQ may target one vendor or broadcast to a category, enforced by CHECK (vendor_id IS NOT NULL OR category_id IS NOT NULL). user_id is nullable so guests can request a quote without registering, with contact fields required instead.

7 · Messaging
conversations, messages, notifications

UNIQUE (vendor_id, user_id, listing_id) on conversations means one thread per buyer-seller-listing triple, so you cannot accidentally fork a conversation.

notifications is an outbound queue: rows are written first with status = 'queued' and dispatched by a worker later, so a failed SMS is retryable rather than lost. The worker does not exist yet.

8 · Reviews and moderation
reviews, reports

UNIQUE (vendor_id, user_id) — one review per person per shop. Rating is 1–5, body is optional (a rating with no text still counts toward the average but has nothing to display).

reports is deliberately polymorphic: report_target_type + report_target_id with no foreign key, so one queue and one screen handles reported vendors, listings, reviews and messages. The cost is that the database cannot verify the target exists — the API has to.

9 · Analytics
search_logs, vendor_profile_views, audit_logs

search_query_normalised is the case-folded form used for grouping. The comment in the schema is worth reading: normalisation must preserve combining marks, because Bengali vowel signs and the hasant are marks, not letters, and stripping them shreds the word.

Sessions are identified by a salted rotating hash, never an IP or account id, so the analytics stay aggregate.

The four views — where the derived data lives

A view is a saved query that behaves like a table. Putting the derivations here rather than in Express means every caller gets the same rating calculation and the same approval filter, and there is exactly one place to fix if it is wrong.

v_business_cards — the one you will read most

This is the shared projection behind every business list on the site: home page, search results, related shops. Reading from it is what makes "approved only" impossible to forget.

database/baseline/schema.sqlabridged
CREATE VIEW v_business_cards AS
SELECT v.vendor_id, v.vendor_slug, v.vendor_name, …
       v.vendor_verified_at IS NOT NULL        AS is_verified,
       loc.location_name                       AS area_name,
       cat.category_name                       AS primary_category,
       COALESCE(r.avg_rating, 0)::numeric(2,1) AS rating,
       COALESCE(r.review_count, 0)             AS review_count,
       h.open_state, h.close_time_today
FROM vendors v
LEFT JOIN locations loc ON loc.location_id = v.location_id

-- primary category = the vendor's category with the lowest sort order
LEFT JOIN LATERAL (
    SELECT c.category_name, c.category_name_bn, c.category_slug
    FROM vendor_categories vc JOIN categories c USING (category_id)
    WHERE vc.vendor_id = v.vendor_id
    ORDER BY c.category_sort_order, c.category_id LIMIT 1
) cat ON TRUE

-- rating and count, computed once, here
LEFT JOIN LATERAL (
    SELECT AVG(review_rating) AS avg_rating, COUNT(*) AS review_count
    FROM reviews
    WHERE vendor_id = v.vendor_id AND review_status = 'published'
) r ON TRUE

-- "open now" for today, evaluated in the database session timezone
LEFT JOIN LATERAL (
    SELECT CASE WHEN oh.hours_is_closed THEN 'closed'
                WHEN oh.hours_is_24h    THEN 'open'
                WHEN LOCALTIME BETWEEN oh.hours_open_time
                                   AND oh.hours_close_time THEN 'open'
                ELSE 'closed' END AS open_state, …
    FROM vendor_opening_hours oh
    WHERE oh.vendor_id = v.vendor_id
      AND oh.hours_day_of_week = EXTRACT(DOW FROM CURRENT_DATE)
) h ON TRUE

WHERE v.vendor_status = 'approved';   -- ← the safety net

Three things to take from that:

  • LEFT JOIN LATERAL is a correlated subquery that can see the outer row (v.vendor_id) and returns columns like a join. ON TRUE is just the required join condition when the correlation already does the matching.
  • open_state is three-valued: 'open', 'closed', or NULL when no hours row exists for today. Null means unknown, and the UI must render nothing rather than "Closed" — a shop shown as closed when it is open is a real cost to that business.
  • The final WHERE is why GET /api/businesses/:slug returns 404 for a pending shop without any explicit check in the route.
ViewPurposeNotable
v_business_cardsPublic card projection for every listApproved-only filter, rating, open state
v_search_trends_dailyPopular-search chips and admin trendsHAVING COUNT(*) >= 5 — suppresses rare terms so one person's query cannot become a "popular search", and cannot re-identify them
v_active_users_dailyDistinct sessions per dayCounts session hashes, never accounts
v_moderation_queueAdmin queueUNION ALL of pending vendors + pending listings + open reports into one list

Two design decisions worth being able to defend

CHECK constraints instead of ENUM types for every status column. Adding a value to a Postgres ENUM requires ALTER TYPE, which has transactional restrictions and is awkward in a migration. Amending a CHECK is one statement.

Trigram (pg_trgm) GIN indexes on vendor_name and listing_title rather than full-text search. This is not a shortcut: PostgreSQL ships no Bengali text-search dictionary, so to_tsvector has no stemmer for half the content. Trigrams work on raw character sequences and are language-agnostic, so they handle রাজশাহী and "Rajshahi" the same way.

Connecting to Postgres

Where the credentials live, how the pool is created, and what each failure code means.

Step 1 — the credentials

They live in backend/.env, which is gitignored. Copy the example and fill in your own Postgres password:

Step 2 — the pool

The entire connection layer is eleven lines. dotenv loads the .env file into process.env, and pg.Pool reads it:

backend/db.jsthe whole file
const { Pool } = require('pg');
require('dotenv').config();

const pool = new Pool({
    host:     process.env.PGHOST,
    user:     process.env.PGUSER,
    password: process.env.PGPASSWORD,
    database: process.env.PGDATABASE,
    port:     process.env.PGPORT,
});

module.exports = pool;

A pool, not a single connection. Opening a TCP connection to Postgres and authenticating costs tens of milliseconds; doing that per request would dominate the response time. The pool keeps a small set of connections open and hands one to each pool.query() call, returning it afterwards. Every route file does require("../db") and gets this same shared pool — Node caches modules, so there is exactly one pool in the process.

Note it connects lazily: creating the pool does not touch the database. The first failure you see will come from the first query, which is why the startup check in the next section exists.

Step 3 — loading the schema

npm run db:load runs backend/scripts/load-db.js, which does four things in order:

  1. 1
    Checks the baseline files exist

    database/baseline/schema.sql and seed.sql. Fails before touching the database rather than half way through.

  2. 2
    Connects to the postgres maintenance database

    You cannot CREATE DATABASE from inside the database you are creating, so it connects to postgres first. With --reset it also runs pg_terminate_backend to kick open connections — a single pgAdmin tab left open will otherwise block DROP DATABASE.

  3. 3
    Applies the schema, then the seed

    The baseline is a full schema dump, so it only loads into an empty database; db:load refuses otherwise and points you to db:reset. The seed wraps its inserts in transactions.

  4. 4
    Copies the seed images

    From database/seed-assets/ into backend/uploads/, so seeded listings and covers show photographs.

  5. 5
    Verifies and prints row counts

    Runs database/checks/verify-baseline.sql, then prints businesses / listings / categories / events / moderation queue — so a silent partial load is visible immediately.

Step 4 — proving it worked

Connecting successfully proves almost nothing: SELECT NOW() works fine against a completely empty database, while every data endpoint returns 500. So the API checks the schema separately, in one round trip:

backend/lib/verifySchema.jscore of it
const { rows } = await pool.query(
    `SELECT n AS name, to_regclass(n) IS NOT NULL AS present
     FROM unnest($1::text[]) AS n`, [names]
);

04

The backend

Express 5, CommonJS, no ORM. Raw parameterised SQL, five files.

Boot sequence — backend/index.js

Middleware in Express runs in the order it is registered, and each one either handles the request or calls the next. This order matters:

  1. 1
    cors({ origin: allowedOrigins, credentials: true })

    Browsers refuse cross-origin responses unless the server says the origin is allowed. CORS_ORIGIN is a comma-separated list, deliberately never * — a wildcard is invalid for credentialed requests and would let any site read the session cookie once auth exists.

  2. 2
    express.json()

    Parses a JSON request body into req.body. Without it every POST handler sees undefined.

  3. 3
    express.static on /uploads

    Serves the files in backend/uploads/ directly over HTTP. This is what makes the paths stored in listing_photos.photo_url resolvable as image URLs in the browser.

  4. 4
    Three routers

    /api/vendors → vendors router, then /api → listings router, then /api → public router. Order matters: a request for /api/vendors/3/listings hits the vendors router first, finds no match, and falls through to the listings router mounted at /api.

  5. 5
    /api/health and /

    Registered last, but no router claims those paths so they are reached.

  6. 6
    app.listen(PORT) + schema report

    An EADDRINUSE handler prints the npx kill-port remedy and exits, instead of dumping a stack trace.

The public endpoints

All of backend/routes/public.js is read-only and returns approved rows only, either through an explicit status filter or by reading v_business_cards.

GET /api/health

Liveness plus schema completeness. 200 when usable, 503 otherwise.

GET /api/home

Returns { categories, featured, events, popularSearches } — everything the home page needs in one request.

Four queries issued concurrently via Promise.all, so the response takes as long as the slowest one rather than the sum of all four. Any single failure fails the whole response: a home page missing its featured shops should not be served as if it were valid.

The category tiles derive their subtitle by string-aggregating the first three child categories, rather than storing a caption — so renaming a subcategory can never leave a stale subtitle on the tile.

GET /api/categories

The full active category tree, flat, with parent ids. The client assembles the hierarchy.

GET /api/businesses
?q &category &area &sort &limit &offset

Search and browse. Returns { results, sponsored, total, limit, offset, sort, facets }. Five queries in parallel: organic page, sponsored, total count, area facets, category facets.

Sponsored rows come back in their own array — never merged into results — so the client structurally cannot render paid placement as an organic hit. They are also excluded from the organic query (WHERE NOT vendor_is_featured), so a featured shop cannot appear twice on one page, and they are limited to two rows on the first page only.

GET /api/businesses/:slug

One profile. Fetches the card row first (404 if absent), then fans out nine parallel queries: contact details, categories, opening hours, photos, listings, facts, reviews, rating distribution, and nearby similar shops.

Addressed by slug, not id, so URLs read /business/rajshahi-silk-house — descriptive and indexable.

Three techniques in the search endpoint worth understanding

Parameterised SQL — why $1 and never string concatenation

backend/routes/public.jsthe q filter
if (q) {
    params.push(`%${q}%`);
    where.push(`(
        v_business_cards.vendor_name ILIKE $${params.length}
        OR v_business_cards.vendor_name_bn ILIKE $${params.length}
        OR v_business_cards.vendor_description ILIKE $${params.length}
        OR EXISTS (
            SELECT 1 FROM vendor_listings l
            WHERE l.vendor_id = v_business_cards.vendor_id
              AND l.listing_status = 'approved'
              AND (l.listing_title ILIKE $${params.length}
                   OR l.listing_title_bn ILIKE $${params.length})
        )
    )`);
}

The user's text goes into the params array and the SQL only ever contains the placeholder $1. Postgres receives the query and the values separately, so a search for '; DROP TABLE vendors; -- is looked up as a literal shop name. That is SQL injection prevention, and it is not optional.

Note also the EXISTS subquery: searching matches a shop's listing titles as well as its name, so a query for "silk saree" finds a shop called Rajshahi Textiles.

The whitelist that lets you sort safely

backend/routes/public.jssort resolution
const SORTS = {
    relevance: "vendor_is_featured DESC, rating DESC, review_count DESC, vendor_name",
    rating:    "rating DESC, review_count DESC, vendor_name",
    reviews:   "review_count DESC, rating DESC, vendor_name",
    name:      "vendor_name",
};
const sort = SORTS[req.query.sort] ? req.query.sort : "relevance";

An ORDER BY clause cannot be parameterised — $1 only stands in for values, not for identifiers. So the incoming sort string is used as a key into a fixed object, and anything unrecognised silently becomes relevance. The user's text never reaches the SQL. The same problem with LIMIT/OFFSET is handled by clamping: Math.min(parseInt(…) || 20, 50) — an integer, capped, so a request for a million rows cannot exhaust the database.

Facets that narrow as you filter

The sidebar counts ("Kazla 12, Laxmipur 8") are computed against the currently active filter, by reusing the same where clause with the view aliased as b:

backend/routes/public.jsfacet reuse
${whereSql ? whereSql.replace(/v_business_cards/g, "b") : ""}

This is why the filter conditions were written with fully table-qualified column names in the first place: the facet queries join vendors, where a bare vendor_name would be ambiguous, and the qualifier can simply be rewritten to the alias.

Error responses that help without leaking

backend/routes/public.jserrorBody()
function errorBody(message, err) {
    if (process.env.NODE_ENV === "production") return { error: message };
    return {
        error: message,
        detail: err.message,
        hint: err.code === "42P01"
            ? "A table or view is missing. Run `npm run db:load`."
            : undefined,
    };
}

In development you get the real Postgres message and a remedy. In production you get only the summary, because a raw database error names your tables and columns to anyone who can trigger it.

File uploads — routes/vendorListings.js

multer handles multipart/form-data. Files are written to backend/uploads/ under a generated name (Date.now() + a random number + the original extension) so two people uploading photo.jpg do not collide, and a fileFilter rejects anything that is not JPEG or PNG. The path is then inserted into listing_photos.photo_url, and express.static serves it back.

Dependency present, never used

socket.io is in backend/package.json but is not imported anywhere. It was presumably intended for the real-time messaging feature. Nothing depends on it today.

The frontend

Next.js 16 App Router, TypeScript, Tailwind 4. Server-rendered, bilingual, and built to be crawlable.

Route groups — four folders for three roles

A folder in parentheses is a route group: it organises files without contributing a URL segment. So app/(public)/page.tsx serves /, not /public.

app/

(public)/               BROWSING — readable signed out, crawlable
  page.tsx                /
  search/page.tsx         /search
  business/[slug]/        /business/<slug>
  vendors/register/       /vendors/register

  layout.tsx              auth gate (TODO)

  layout.tsx              stricter gate (TODO)
  admin/                  /admin

Four groups for three roles, because the customer has two halves that need different gates. (public) is the customer browsing — search, categories, shop profiles — which must stay readable signed out and indexable. (seeker) is the same person signed in: saved shops, their quote requests, messages, their reviews.

Splitting on the access rule rather than on the person buys two things. Public URLs stay clean — a shop is /business/rajshahi-silk-house, not /customer/business/…. And there is one gate per area: the auth check lives in the group's layout.tsx, so every page in the folder is protected by default and nobody has to remember to add a check to a new screen.

Registration sits in (public) on purpose — you are not a vendor yet when you sign up, so it must be outside the provider gate.

All three gates are empty

Every layout.tsx in (seeker), (provider) and (admin) contains a TODO(auth) comment and return children. Anyone can open /admin and /vendors/dashboard today. The intended code is written out in the comments and waits only on sessions existing.

The layout chain, and the one thing it cannot do

Next composes layouts outward-in: the root app/layout.tsx renders <html>, the Geist font variable and the site-wide metadata; the group layout wraps the page. But layouts do not receive searchParams — and the language in this app is a query parameter (?lang=bn).

That is the whole reason AppShell exists as a component instead of a layout. Each page resolves the locale itself and passes it down:

app/(public)/page.tsxthe pattern every public page follows
export default async function HomePage({ searchParams }: {
    // a Promise in Next 15+, so it must be awaited
    searchParams: Promise<{ lang?: string }>;
}) {
    const [{ lang }, data] = await Promise.all([searchParams, getHomeData()]);
    const locale = resolveLocale(lang);

    return (
        <AppShell locale={locale} current="/">
            <Hero locale={locale} />
            <CategoryGrid locale={locale} categories={data.categories} />
            <FeaturedBusinesses locale={locale} businesses={data.featured} />
            …
        </AppShell>
    );
}

Two details there. Promise.all([searchParams, getHomeData()]) resolves the params and the network call together rather than one after the other. And there is no useEffect, no state, no loading branch — the function returns finished markup.

The four lib/ files

lib/api.ts

The only place in the frontend that knows the API exists. Three functions — getHomeData(), searchBusinesses(), getBusiness(slug) — plus assetUrl(). All run on the server.

lib/types.ts

The API contract as TypeScript interfaces, with field names matching the database columns exactly. Rename a column in Express without updating this and npm run typecheck fails — the mismatch surfaces as a compile error rather than as blank fields at runtime.

One footgun documented here: pg returns NUMERIC as a string, not a number, because JavaScript's float cannot represent every NUMERIC exactly. So rating is typed string | number and must go through toNumber() before any comparison — "4.5" > 4 is a string comparison and will surprise you.

lib/i18n.ts

Every string in English and Bangla, plus three helpers: resolveLocale() reads ?lang=, localeHref() appends it to a link so the language survives navigation, and pick(locale, en, bn) chooses a database field and falls back to the other language if the translation is null — a field is never rendered empty.

No hardcoded English in JSX. That is a hard rule here.

lib/format.ts

Display formatting, server-side only. toNumber, formatRating, formatClockTime (SQL TIME → "9:30 AM"), event date helpers pinned to Asia/Dhaka, and localiseDigits, which maps ASCII digits to Bengali numerals (০১২৩৪৫৬৭৮৯) when the Bangla locale is active.

Timezone is pinned deliberately: formatting the same date on the server and again in the browser produces a hydration mismatch whenever the two timezones differ.

Forms that work without JavaScript

The header search and the search-page filters are plain <form action="/search" method="get">. Submitting one navigates to /search?q=silk&category=textiles&area=kazla, which the server renders. No client state, no fetch, no onSubmit.

Three consequences, all of them wanted: every filter combination is a distinct URL that can be bookmarked, shared and crawled; the pages stay server components; and the site works with JavaScript disabled. The locale rides along as a hidden field so ?lang=bn is not lost on submit.

Styling — Tailwind 4 tokens

Design tokens are declared in the @theme block of app/globals.css, and Tailwind generates utilities from them: --color-brand-600 produces bg-brand-600, text-brand-600 and border-brand-600. Components use those utilities, never raw hex and never new CSS classes.

Two traps documented in the repo, both of which have already cost someone an afternoon:

  • Class names must appear complete in the source. Tailwind scans files as text, so `bg-${colour}-50` is never generated. Write the full strings out.
  • Plain CSS outside @layer beats utility classes. A padding shorthand in an unlayered rule silently overrode pl-11 and pushed the search text underneath its own icon.

Icons come from two libraries on purpose: lucide-react for all UI icons, imported directly so tree-shaking drops the rest; @icons-pack/react-simple-icons for brand marks only (Facebook, WhatsApp), because Lucide removed trademarked logos. components/shared/icons.ts exists solely for categories.category_icon, which is a string in the database and so can only be resolved at runtime.

SEO, which is a client requirement rather than a nicety

  • Per-page metadata. The profile page's generateMetadata() builds a title from the shop's real name, category and area, and emits per-business OpenGraph tags with the cover photo for link previews.
  • Structured data. The home page emits WebSite JSON-LD with a SearchAction (this is what produces a sitelinks search box). The profile page emits LocalBusiness with address, geo coordinates, opening hours and aggregate rating.
  • Only populated fields are emitted. An aggregateRating with a zero review count is invalid structured data and is reported as an error by search engines rather than ignored — so it is omitted when reviewCount === 0.
  • Search results are noindex, follow. Arbitrary queries would generate unbounded near-duplicate pages, but links are still followed so the profiles get discovered.
06

How the two halves connect

One environment variable, one fetch wrapper, and a deliberate split between what the server can reach and what the browser can.

The two base URLs, and why there are two

API_BASE_URL
no NEXT_PUBLIC_ prefix

Where the Next server reaches Express. Because it lacks the NEXT_PUBLIC_ prefix, Next never sends it to the browser — it exists only in the server process. In Docker this becomes the service name, e.g. http://api:4000, a hostname no browser could ever resolve.

NEXT_PUBLIC_ASSET_BASE_URL

Where the browser loads uploaded images from. This one is exposed, because it ends up in an <img src> that the user's browser must fetch itself.

NEXT_PUBLIC_SITE_URL

The public site address, used for canonical links, JSON-LD URLs and OpenGraph cards. Leaving this as localhost in production breaks every share preview.

That split is the whole point of the NEXT_PUBLIC_ convention: anything with the prefix is inlined into the JavaScript bundle and is public; anything without it stays on the server.

The fetch wrapper

frontend/lib/api.tsevery request goes through this
const API_BASE = process.env.API_BASE_URL || "http://localhost:4000";

async function getJson<T>(path: string, revalidateSeconds: number): Promise<T> {
    const res = await fetch(`${API_BASE}${path}`, {
        next: { revalidate: revalidateSeconds },
        headers: { Accept: "application/json" },
    });
    if (!res.ok) throw new ApiError(res.status, path);
    return res.json() as Promise<T>;
}

next: { revalidate: n } is Next's data cache. The response is cached for n seconds; concurrent visitors within that window are served from cache and the API is not called again. Three different windows, chosen by how fast the data changes:

FunctionEndpointCacheOn failure
getHomeData()/api/home300sReturns empty arrays — page renders its shell
searchBusinesses()/api/businesses60sReturns an empty result set
getBusiness()/api/businesses/:slug300snull on 404 → notFound(); throws on anything else

Two different failure policies, on purpose

getHomeData() swallows errors and returns empty collections. If the API is down, the visitor still gets a working header, search box, navigation and footer — degraded, not broken.

getBusiness() does the opposite and rethrows anything that is not a 404. A profile page rendered with half its data missing would look complete and be wrong; better to fail loudly. A genuine 404 becomes Next's notFound(), giving a proper 404 status — which matters, because a "not found" page returning HTTP 200 gets indexed as a real page.

assetUrl — the path fixer

frontend/lib/api.ts
export function assetUrl(storedPath: string | null): string | null {
    if (!storedPath) return null;
    if (/^https?:\/\//i.test(storedPath)) return storedPath;  // already absolute
    const base = process.env.NEXT_PUBLIC_ASSET_BASE_URL || API_BASE;
    return `${base}/${storedPath.replace(/^\/+/, "").replace(/\\/g, "/")}`;
}

The database stores a relative path like uploads/1788451854562-688168547.jpg; the browser needs http://localhost:4000/uploads/…. The final replace(/\\/g, "/") is a Windows patch: the upload route stores file.path, which on Windows contains a backslash and is not a valid URL. Fixing it at the source (storing a URL path at insert time) is on the to-do list.

The legacy pages break this rule

The four "use client" vendor pages call fetch("http://localhost:4000/api/…") directly from the browser, with the URL hardcoded. That is the older pattern, it bypasses lib/api.ts entirely, it is the reason CORS_ORIGIN has to be configured at all, and it will break the moment the app is deployed anywhere other than localhost.

Four full traces

The same journey followed all the way down and back, four times.

A · Someone opens the home page

  1. 1
    Browser requests GET /

    Next matches app/(public)/page.tsx. The route group contributes no URL segment.

  2. 2
    HomePage() runs on the server

    Awaits searchParams and getHomeData() together.

  3. 3
    Cache check

    If /api/home was fetched under 300 seconds ago, the cached JSON is used and steps 4–7 are skipped entirely.

  4. 4
    Server-side fetch("http://localhost:4000/api/home")

    Node to Node. The browser never sees this request, and no CORS check applies — CORS is a browser rule.

  5. 5
    Express matches the public router

    Fires four queries with Promise.all.

  6. 6
    Postgres runs them concurrently

    Category tiles with derived subtitles; five featured cards from v_business_cards; three upcoming published events; the top eight search terms from v_search_trends_daily.

  7. 7
    Express replies with one JSON object

    { categories, featured, events, popularSearches }.

  8. 8
    React renders to HTML on the server

    AppShell → header, side nav, hero, category grid, featured cards, sidebar rails, footer. pick() chooses English or Bangla per field; assetUrl() rewrites every cover path to an absolute URL.

  9. 9
    Complete HTML goes to the browser

    Every shop name and rating is already in the markup, plus the WebSite JSON-LD block. Googlebot needs to run nothing.

B · Someone searches "silk" and filters to Kazla

  1. 1
    The header form submits

    A plain GET form → /search?q=silk. Choosing an area in the filter bar resubmits as /search?q=silk&area=kazla. The search term rides along as a hidden field so it survives the filter change.

  2. 2
    SearchPage computes the page window

    page=2 → offset = 20 at a fixed page size of 20. It fetches the search results and getHomeData() — the category dropdown reuses the already-cached home payload rather than making a second request for it.

  3. 3
    GET /api/businesses?q=silk&area=kazla&limit=20&offset=20

    Express builds the where array and params array together, resolves sort through the whitelist, and clamps limit and offset to integers.

  4. 4
    Five queries at once

    Organic page (WHERE NOT vendor_is_featured), up to two sponsored rows (offset 0 only — this is page 2, so none), the total count including sponsored, area facets, category facets.

  5. 5
    The page renders three distinct blocks

    A labelled sponsored list on top, then organic results, then the facet sidebar. If both arrays are empty it renders the "no results" panel with a clear-all link instead.

  6. 6
    Pagination is derived, not counted

    hasMore = results.length === PAGE_SIZE, because total includes sponsored rows that are not part of the paginated set.

C · Someone opens a shop profile

  1. 1
    GET /business/rajshahi-silk-house

    Matches app/(public)/business/[slug]/page.tsx. generateMetadata() runs first and calls getBusiness(slug) — the second call from the page body hits the same cache entry, so this is one network request, not two.

  2. 2
    Express looks the slug up in v_business_cards

    Joined to vendors for the coordinates the card view omits. No row → 404. Since the view is approved-only, a pending shop 404s without any explicit status check.

  3. 3
    Nine parallel queries

    Contact details · categories · opening hours · gallery photos (drawn from approved listings) · listings · facts · the five most recent written reviews · the 1–5 rating distribution · four nearby shops sharing a category.

  4. 4
    Distance without PostGIS

    Nearby shops are ordered by an equirectangular approximation: 111.045 × √(Δlat² + (Δlng × cos(lat))²). Accurate enough across one city, and it avoids a PostGIS dependency for a single sort.

  5. 5
    Rating distribution is filled in

    Postgres returns only the ratings that occur; Express maps them onto [5,4,3,2,1] with zeros, so the bar chart always has five bars.

  6. 6
    Profile and sidebar render, plus JSON-LD

    LocalBusiness structured data with address, geo, opening hours per day, and — only if there is at least one review — an aggregateRating.

D · A vendor adds a listing with photos legacy path

  1. 1
    A client component, in the browser

    add-listing/page.jsx is "use client" with useState form state. This is the old pattern and it is the only write path in the app.

  2. 2
    POST /api/vendors/:vendorId/listings

    Sent from the browser to a hardcoded http://localhost:4000, as JSON. Because it is cross-origin (3000 → 4000), the browser applies CORS — which is why CORS_ORIGIN must list http://localhost:3000.

  3. 3
    Insert, returning the new id

    INSERT … RETURNING listing_id — one round trip to write the row and learn its id, which the next step needs.

  4. 4
    POST /api/listings/:listingId/photos

    A second request, this time multipart/form-data. Multer writes each file to backend/uploads/ under a generated name and rejects anything that is not JPEG or PNG.

  5. 5
    One listing_photos row per file

    Then express.static serves them back at /uploads/<name>.

This trace does not currently work

Steps 3 and 5 fail against the v2 schema. The insert names title, description, price and category — columns that existed in the superseded database/schema.sql and are now listing_title, listing_description, listing_price and category_id. Postgres answers 42703: column "title" of relation "vendor_listings" does not exist. See the next section.

What is broken, and what is simply missing

Tracked here so nobody rediscovers them. Broken means it throws today; missing means it was never built.

Broken: the two legacy routes still speak the old schema

Both were written against database/schema.sql, which schema.v2.sql replaced. The columns moved and nothing updated the SQL.

RouteSendsv2 expects
POST /api/vendorsvendor_passwordNot a column. Credentials belong on users, hashed
vendor_citylocation_id, resolved against locations
— nothing —vendor_slug is NOT NULL UNIQUE; user_id is NOT NULL
POST /…/listingstitle, description, price, categorylisting_title, listing_description, listing_price, category_id

Two further problems in the same area:

  • GET /api/vendors does SELECT * FROM vendors with no status filter. On the v2 table that now returns vendor_rejection_reason and moderation state to any anonymous caller. It needs WHERE vendor_status = 'approved' and an explicit column list.
  • The photo insert stores file.path — an OS-specific path with a backslash on Windows. It should store a URL path (uploads/<filename>), which is the form the seed data assumes and what assetUrl() currently patches around.

database/SCHEMA-NOTES.md §4 spells out the fix route by route and estimates it at about an hour.

Missing: authentication, and everything waiting behind it

users, otp_codes and sessions exist in the schema. Nothing writes to them. Consequently:

  • All three role gates are empty return children. /admin and /vendors/dashboard are open to anyone. This must not ship.
  • The bookmark button on every business card links to /login, which does not exist — the saved_businesses table is ready and unused.
  • RFQ, messaging, reviews and the whole admin surface all wait on knowing who the user is.
  • The vendor dashboard fills a <select> with every vendor and auto-selects the first, because there is no session to say which vendor you are.

Missing: pages linked in the navigation but never built

Categories, deals, events and blog appear in the nav and in sidebar links, and they 404. /admin and /account render placeholder pages that document what belongs there and which tables back it.

Known limitations, accepted for now

  • Language is ?lang=bn. Reading a search parameter opts a page out of static generation. Crawling is unaffected — the server-rendered markup is complete either way — but the static cache is not used. Locale-prefixed routes (/en, /bn) are the fix, and would also give each language a distinct indexable URL.
  • Maps are hand-drawn SVG sketches, not real maps. A live map needs an API key the client has not provided; Leaflet with OpenStreetMap tiles needs no key and is the intended swap.
  • /api/home is cached for five minutes. After changing seed data, restart the frontend or delete frontend/shahebbazar/.next — otherwise you will spend twenty minutes debugging a stale payload.
  • No ER diagram yet, though it is a required deliverable. It can be generated from the schema with pgAdmin's ERD tool or dbdiagram.io.
